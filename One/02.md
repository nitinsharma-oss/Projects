## 2. A correction to Step 1

Step 1 claimed the three ownership invariants could be expressed as composite foreign keys where
`MATCH SIMPLE` disables each one for the ownership shape it doesn't govern. **That was right in
principle and wrong in detail**, and running the DDL is what exposed it.

The draft personal-ownership key was:

```sql
FOREIGN KEY (profile_id, holder_account_id) REFERENCES profiles (id, owner_account_id)
```

The reasoning was that this stands down for organisation-owned cards because `owner_account_id`
is NULL. It does not. **`MATCH SIMPLE` only stands a constraint down when a column inside the key
is NULL** — and `owner_account_id` is not in that key. On an org card both `profile_id` and
`holder_account_id` are populated, so the constraint fires, looks for a profile owned by the
holder, finds an org-owned profile instead, and rejects the insert. Organisation cards would have
been impossible to create.

The fix puts the discriminator *inside the key*, as a generated column:

```sql
personal_holder_id uuid GENERATED ALWAYS AS (
    CASE WHEN owner_account_id IS NOT NULL THEN holder_account_id END
) STORED

FOREIGN KEY (profile_id, personal_holder_id) REFERENCES profiles (id, owner_account_id)
```

Generated, so it cannot drift from `owner_account_id`. NULL for org cards, so the key stands down
exactly as intended. The two org-side keys were already correct, because `owner_org_id` genuinely
is one of their columns.

This is the kind of error that survives any amount of review and dies on first execution.

## 3. The ownership invariants, as shipped

```sql
-- exactly one owner
CHECK (num_nonnulls(owner_account_id, owner_org_id) <= 1)

-- personal card: the profile must belong to the holder
FOREIGN KEY (profile_id, personal_holder_id)      REFERENCES profiles (id, owner_account_id)

-- org card: the profile must belong to the owning organisation
FOREIGN KEY (profile_id, owner_org_id)            REFERENCES profiles (id, owner_org_id)

-- org card: the holder must be a member of the owning organisation
FOREIGN KEY (holder_account_id, owner_org_id)     REFERENCES org_memberships (account_id, org_id)
```

Three declarative keys, no triggers, no application logic. The §2.6 decision — organisation cards
may not point at personal profiles — is enforced by the database, verified by test, and readable
by an auditor in four lines.

Making these referenceable required two non-partial unique constraints on `profiles`:
`(id, owner_account_id)` and `(id, owner_org_id)`. Both are redundant given `id` is the primary
key, which is exactly why they cost nothing. **Postgres will not let a foreign key reference a
partial unique index** — the first draft used partial indexes and failed to apply.

## 4. Decisions made during implementation

### 4.1 Tokens are stored hashed, never in plaintext

`cards.token_hash` is the unique key; the resolver hashes the incoming token and looks up the
hash. A database disclosure therefore does not hand an attacker a catalogue of live tokens mapped
to identities.

*Trade-off:* nobody can ever display a token, including support. Mitigated by `token_prefix` —
six unhashed characters, indexed, enough for "the card ending in 4F2A" without being enough to
resolve anything.

### 4.2 One table owns the entire slug namespace

`slugs` holds current slugs, retired slugs, **and** platform reservations, all colliding on one
primary key. A retired slug can never be reissued to a different profile, so every link ever
shared keeps resolving to the same identity — permanently, by construction rather than by policy.

Reservations are rows with no profile, which blocks `admin`, `billing`, `support` and friends
without a trigger. The first draft used a separate `reserved_slugs` table and a check constraint
containing a subquery; Postgres rejects subqueries in check constraints, and the single-namespace
design is better anyway.

Reserved slugs may be short (claiming `t` and `u` is the point); user slugs require three
characters or more.

### 4.3 `profiles.current_slug` is a deferred foreign key

A profile and its first slug reference each other, so the constraint is `DEFERRABLE INITIALLY
DEFERRED` and **both must be written in one transaction**. This is a real obligation on the
repository layer, not a test artifact — it surfaced when psql's autocommit broke the fixtures.

### 4.4 `tap_events` partitions by region first, then month

You did not answer the residency question, so this takes the extensible option: `LIST (region)`
subpartitioned by `RANGE (occurred_at)`.

*Trade-off:* an unused dimension adds partition-management overhead now. Against: adding a region
dimension to 1.2 billion existing rows is among the most expensive migrations in this class of
system. Carrying it costs a rounding error; retrofitting it costs a quarter.

`tap_events` deliberately has **no foreign keys**. At ingest volume an FK check per row is pure
overhead, and cards are `RESTRICT`-protected everywhere else.

### 4.5 `audit_log` deliberately has no foreign key to `accounts`

An FK would force `ON DELETE` semantics on a table that must never lose rows, and would let
account deletion cascade into the audit trail. Integrity here is one-directional by design:
accounts are tombstoned, never deleted, so the reference can never dangle.

### 4.6 Erasure and immutable audit, verified together

`accounts` carries a check constraint making the two states mutually exclusive: a live account
must have an email; a tombstoned one must have email, password hash and name all NULL. Erasure
cannot be half-done.

Email uniqueness is a **partial** unique index over live accounts only, so tombstoning frees the
address for reuse. Three tests cover this: tombstoning with data remaining is rejected, proper
tombstoning is accepted, and the audit row referencing the erased actor is asserted to still
exist afterwards.

### 4.7 Append-only is a grant, not a convention

```
audit_log            INSERT, SELECT
card_encodings       INSERT, SELECT
ownership_transfers  INSERT, SELECT
profiles             DELETE, INSERT, SELECT, UPDATE
```

`app_rw` physically cannot rewrite history. Seven tests run **as that role** and confirm each
attempt fails. An auditor verifies this with `\dp` rather than by reading code.

`app_resolver` is narrower still — column-level `SELECT` on three columns of `cards` and nothing
else. A resolver compromise cannot read profiles, accounts, or tokens for other cards.

## 5. Resolver performance, measured

The claim was a single indexed row read. Measured against 300,000 cards:

```
Index Only Scan using cards_resolver_idx on cards (actual time=0.051..0.052 rows=1)
  Index Cond: (token_hash = '\x89d2...'::bytea)
  Heap Fetches: 1
  Buffers: shared hit=4
```

Index-only scan, four buffer hits, ~0.05 ms. `INCLUDE (serving_state, serving_slug)` is what
keeps it index-only — the resolver never touches the heap for a cached page, and never joins.

At 12M rows the index stays comfortably resident. This is why the peak of ~800 req/s from §1 is
not a scaling concern; the cache in front of it is for burst absorption and negative-lookup
defence, not for relieving the database.

## 6. Operational obligations this schema creates

These are not optional extras; the schema is incorrect in production without them.

| Obligation | Why | Cadence |
| --- | --- | --- |
| Create next month's partitions | Writes fail when no partition matches | Monthly, automated, alerted |
| Drop expired partitions | Retention is enforced by dropping, not deleting | Monthly |
| Refresh `tap_daily` rollups | Dashboard reads only rollups | Hourly |
| Reconcile `serving_state` | It is a cache and caches drift (§2.2) | Rolling; non-zero drift is an alarm |
| Expire `idempotency_keys`, `otp_codes`, dead `sessions` | Unbounded growth | Daily |
| Process `stripe_events` backlog | Partial index tracks unprocessed | Continuous, alerted |
| `VALIDATE CONSTRAINT` after backfills | Expand/contract leaves `NOT VALID` constraints | Per migration |

`audit_log_default` and the absence of a default `tap_events` month partition are intentional:
audit rows must never be lost, so they fall into a default partition; tap events must never
silently land in an unmanaged partition, so a missing month fails loudly. One test asserts this.

## 7. Migration order

```
01  extensions, enums
02  organizations, accounts, org_memberships
03  sessions, otp_codes
04  profiles, slugs (+ reservations seed)
05  card_batches, cards            <- generated column, three composite FKs
06  ownership_transfers, card_assignments, card_encodings
07  subscriptions, stripe_events, idempotency_keys
08  audit_log (+ partitions)
09  tap_events (+ region/month partitions), rollups
10  roles and grants               <- last: grants reference every table
```

Every subsequent change ships expand/contract: add nullable, backfill in batches, dual-write,
switch reads, drop old. At 12M cards and 1.2B events there is no window for a blocking `ALTER`.
New constraints are added `NOT VALID` and validated separately, so validation does not hold an
`ACCESS EXCLUSIVE` lock.

## 8. Deliberately deferred

- **Row-level security.** Considered and deferred. Tenant isolation is currently enforced by the
  composite keys plus application scoping. RLS on `profiles` and `cards` is the right hardening
  for a multi-tenant audit, but it interacts badly with connection pooling in transaction mode
  and needs a session-variable strategy designed first. Step 3.
- **Column encryption at rest** for `password_hash` and `claim_code_hash` — both are already
  irreversible digests; disk encryption covers the rest. Revisit if the audit asks for envelope
  encryption.
- **`pg_partman`** rather than hand-rolled partition management. An operational choice, not a
  schema one.

## 9. Open items

1. **Data residency** (§4.4) — the region enum is currently `eu / us / in`. Confirm the target
   markets; adding a region later is cheap, removing one is not.
2. **Retention window for `tap_events`** — the partition-drop machinery exists; the number does
   not. This is a legal and product decision, not a technical one, and it belongs in the privacy
   policy before launch.
3. **Reserved slug list** — twelve entries seeded. Trademark and impersonation terms should be
   reviewed by whoever owns brand risk.
